Módulo 10

Automatización y toolkit

Qué automatizar primero para que el grafo se mantenga sano sin vigilancia manual, y qué ofrecen el CLI, los siete comandos y el asistente del toolkit.

45 minArquitecturaDesarrollo

Un grafo que se cuida solo

En L1 la calidad de las specs depende de que alguien se acuerde de revisarlas. A partir de L2 el objetivo cambia: que el grafo se mantenga sano sin que nadie tenga que vigilarlo. Se consigue con tres capas de automatización, de la más cercana a quien escribe a la más corporativa: hooks locales, pipeline de CI y coordinación entre repositorios.

Hooks locales

Dos hooks de Git cubren los dos momentos en que el grafo puede romperse en tu máquina.

El pre-commit se ocupa de lo que sale. Solo actúa cuando el commit lleva specs en staging, de modo que los commits que únicamente tocan código no pagan ningún coste:

# .githooks/pre-commit
STAGED=$(git diff --cached --name-only --diff-filter=ACM | grep '^specs/.*\.md$')
[ -z "$STAGED" ] && exit 0
node apps/spec-graph/spec-graph.mjs --specs specs validate || {
  echo "Validación fallida. Corrige antes de commitear."; exit 1; }

El post-merge se ocupa de lo que entra. Tras cada pull reconstruye el grafo y muestra el impacto de los cambios recibidos, que detecta comparando con ORIG_HEAD. Así te enteras de que una regla de la que depende tu trabajo ha cambiado en el momento en que llega, no tres días después.

Los hooks viven en el repositorio y cada persona los activa una vez por clon:

git config core.hooksPath .githooks

Pipeline de CI

El hook local es una cortesía; el CI es la garantía, porque no depende de que cada persona lo haya activado. La política habitual es esta:

PasoComportamiento
validateBloquea el PR y hace fallar el job
orphansAvisa pero no bloquea; a partir de L3 conviene bloquearlo también
upgrade-impactEn los PR que tocan specs de conocimiento, publica el resultado como comentario para avisar a los equipos afectados
Publicación del grafoGenera graph.html y lo publica como artefacto de CI o en GitHub Pages

Idea clave. Los errores bloquean y los avisos informan. Si todo bloquea, el equipo acaba buscando la forma de saltarse el control; si nada bloquea, las referencias rotas llegan a la rama principal.

Varios repositorios

Cuando varios equipos comparten conocimiento, el patrón dominante separa lo persistente de lo efímero. El conocimiento (DOM, ARCH, PROD) vive en un repositorio central compartido. Los artefactos de trabajo viven en el repositorio de cada equipo, que incorpora el central como submódulo en .specs/.

central-specs/            conocimiento compartido: DOM, ARCH, PROD

proyecto-pagos/
├── .specs/               submódulo que apunta a central-specs
└── specs/                artefactos de trabajo del equipo

Queda por resolver cómo se entera un equipo de que el conocimiento central ha cambiado bajo sus pies. El hook post-merge del repositorio de proyecto lanza:

spec-graph upgrade-impact --dep .specs --scope work

El comando compara dos referencias de Git e informa de qué trabajo local queda afectado por lo que ha entrado aguas arriba.

Qué automatizar en cada nivel

AutomatizaciónNivelPrioridad
Hook pre-commit de validaciónL2Alta
Validación en CI bloqueando el PRL2Alta
Reconstrucción del grafo post-mergeL2Media
upgrade-impact en CIL3Alta

Regla práctica. Empieza por las dos primeras filas. El hook de pre-commit y la validación en CI dan valor desde el primer día; el resto gana importancia a medida que más equipos se suman.

El toolkit

Para que un equipo adopte KDD sin clonar el repositorio completo del framework existe un toolkit distribuible con tres piezas: el CLI, siete comandos de barra y un agente conversacional. Está disponible para Claude Code, Gemini y GitHub Copilot.

Los siete comandos

ComandoPara quéCuándo usarlo
spec-validateInforme de salud: referencias rotas, huérfanos, specs caducadasAntes de un PR o tras una edición masiva
spec-graphConsultar el grafo: estadísticas, filtros, caminos, impactoAl explorar el panorama de specs
spec-createCrear una spec desde lenguaje naturalPara formalizar conocimiento nuevo con rapidez
spec-impactAnálisis de impacto con clasificación de riesgoAntes de modificar una spec existente
spec-contextEncontrar y sintetizar las specs relevantes para una tareaPara saber qué conocimiento hay disponible
spec-activatePipeline completo de activación y prompt listo para el agenteAl alimentar agentes, de L4 en adelante
spec-consolidateConsolidación posterior al trabajo: ADR, actualizaciones, conocimiento nuevoAl completar una WRK-SPEC

Referencia del CLI

El CLI es la pieza determinista: no interpreta, comprueba. Sus comandos se agrupan por lo que quieres conseguir.

Salud del grafo

ComandoQué hace
validateValida todas las specs: campos obligatorios, referencias existentes, valores permitidos y coherencia de relaciones. Es el que bloquea el PR
orphansLista las specs que nadie referencia y que no referencian a nadie. Corre como aviso
statsEstadísticas: specs por capa, distribución de confianza, densidad de relaciones
filterFiltra por capa, etiqueta, nivel de confianza derivado o specs caducadas

Navegación e impacto

ComandoQué hace
context <id> --depth NCalcula el contexto alrededor de una spec siguiendo sus dependencias. Es la base de la activación transitiva
impact <id>Lista todo lo que depende de la spec indicada: qué se rompe si la cambias
upgrade-impactCompara dos referencias de Git y reporta qué trabajo se ve afectado por los cambios de conocimiento que han entrado
path <a> <b>Camino más corto entre dos specs

Activación

ComandoQué hace
resolve <manifiesto>Resuelve un manifiesto de activación con unos parámetros dados e imprime qué activaría y qué sugeriría
new-task <tipo>Resuelve el manifiesto y escribe una WRK-SPEC con la activación ya congelada
bootstrap <wrk-spec>Compone el plan de arranque de una WRK-SPEC congelada. En simulación planifica sin escribir nada

Flujos

ComandoQué hace
new-run <flow-id>Lanza un flujo: valida los parámetros contra su esquema y escribe la WRK-SPEC, el WRK-PLAN y una WRK-TASK por paso
run-status <wrk-spec>Paso actual, intentos, decisiones humanas abiertas y tomadas, y coste de una ejecución. Solo lectura

Proyecciones y distribución

ComandoQué hace
check-projectionsDetecta proyecciones obsoletas, desviadas o sin bloquear. En modo estricto hace fallar el build
lock <proj-id>Escribe o refresca el bloqueo de una proyección a partir de sus refs fijadas y sus ficheros
vendor <proj-id>Materializa una proyección de tipo copia, byte a byte y con su clausura de dependencias
render <proj-id>Ejecuta el renderizador fijado por una proyección de tipo entregable y escribe su bloqueo
bundle --manifestResuelve un manifiesto y emite su clausura como paquete de distribución reproducible

Evidencia e interoperabilidad

ComandoQué hace
fragmentsLista los fragmentos de captura con su estado y las specs en que se destilaron. El registro es derivado
export-okfExporta el directorio de specs como paquete OKF v0.2 conforme, sin perder la cabecera KDD
import-okf <paquete>Ingiere un paquete OKF externo como specs gobernadas, conservando la cabecera original

Los dos primeros grupos son los de uso diario desde L2. Los demás entran en juego a medida que incorporas manifiestos de activación, flujos, contenido derivado o intercambio con terceros (módulo 7, Confianza y evidencia; módulo 8, Procesos y flujos).

El asistente conversacional

Los comandos resuelven una operación cada uno. El agente conversacional del toolkit guía en lenguaje natural los trabajos de varios pasos, y lo hace con tres recorridos:

RecorridoPasos
Crear conocimientoClasificar → andamiar → redactar → conectar → validar
Crear trabajoAcotar → activar → redactar la WRK-SPEC → descomponer → validar
ConsolidarRevisar → delta → descubrir → confianza

Es la vía más cómoda para quien empieza: no hace falta recordar en qué capa encaja una regla ni qué campos lleva la cabecera, porque el asistente lo pregunta y acaba validando el resultado con el mismo CLI que correrá en CI.

En resumen

  • Desde L2, el objetivo es que el grafo se mantenga sano sin vigilancia manual.
  • En local, un pre-commit valida al salir y un post-merge reconstruye el grafo y muestra el impacto al entrar.
  • En CI, validate bloquea, orphans avisa, upgrade-impact comenta el PR y el grafo se publica.
  • Con varios repositorios, el conocimiento va en uno central y cada proyecto lo incorpora como submódulo en .specs/.
  • El toolkit reúne el CLI, siete comandos y un asistente con tres recorridos: crear conocimiento, crear trabajo y consolidar.

Para practicar

Con el repositorio de tu equipo delante:

  1. Añade el hook de pre-commit y actívalo con git config core.hooksPath .githooks. Provoca un fallo a propósito, por ejemplo una dependencia hacia un id que no existe, y comprueba que el commit se rechaza.
  2. Escribe en una tabla qué pasos de vuestro pipeline de CI deberían bloquear y cuáles solo avisar, y quién recibe cada aviso.
  3. Ejecuta impact sobre la spec más referenciada que tengáis y revisa con el equipo si la lista de afectados coincide con lo que esperabais. Las sorpresas son dependencias que faltan o que sobran.
  4. Localizad en la tabla de automatización la primera fila que aún no tenéis y poned fecha para incorporarla.
