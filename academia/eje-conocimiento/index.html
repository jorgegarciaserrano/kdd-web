Eje de Conocimiento

Cómo clasificar el conocimiento en capas, conectarlo en un grafo y escribir una primera spec que pase la validación.

60 minArquitecturaDesarrolloNegocio

Las cinco capas de partida

El eje de Conocimiento guarda lo que la organización sabe y sigue siendo cierto cuando termina el proyecto. Cada spec se asigna a una capa, y la capa determina quién es su dueño natural y con qué otras specs suele relacionarse.

CapaQué recogePatrón de idRelaciones típicasEjemplo
ARCH ArquitecturaDecisiones técnicas transversales que condicionan muchas funcionalidades a la vezARCH-AREA-NNNRestringe a DOM, PROD y FEATArquitectura orientada a eventos; patrón de API gateway
DOM DominioReglas de negocio y lógica de dominio, propiedad de un experto funcionalDOM-AREA-NNNimplements regulación; constrained-by ARCHReglas de cálculo de VaR; límites de transferencia por tipo de cliente
PROD ProductoCapacidades de producto: qué ofrece la plataforma y a quiénPROD-AREA-NNNRestringe a FEATVisión de la plataforma de analítica de carteras
FEAT FuncionalidadComportamiento concreto de cara al usuarioFEAT-AREA-NNNimplements PROD; uses-data-from DOMCuadro de mando de P&L en tiempo real
DOC DocumentaciónConvenciones, guías y estándares de equipoDOC-AREA-NNNDa soporte a todas las capasConvenciones de nombrado de APIs; guía de incorporación

El eje tiene tres tipos más: PROC (el método de trabajo descrito como conocimiento), FRAG (capturas inmutables de evidencia) y PROJ (contenido derivado de otras specs). Se tratan más adelante (módulo 7, Confianza y evidencia; módulo 8, Procesos y flujos).

Idea clave. No necesitas todas las capas desde el primer día. Muchos equipos trabajan durante meses solo con DOM, ARCH, ADR y los tres artefactos de trabajo.

Cómo elegir capa cuando dudas

Cinco preguntas rápidas resuelven casi todos los casos:

Si la spec...Entonces es
Condiciona muchas funcionalidades a la vezARCH
Tiene como dueño a un experto de negocioDOM
Tiene como dueño al product ownerPROD
Describe comportamiento que ve el usuarioFEAT
Explica cómo se hace algoDOC

Cuando una spec encaja en dos capas, casi siempre son dos specs. Un borrador que mezcla el límite de importe a partir del cual una transferencia necesita doble aprobación con la pantalla que avisa al usuario contiene una regla de dominio (DOM) y un comportamiento visible (FEAT). Sepáralas y conecta la segunda con la primera.

Relaciones: de ficheros sueltos a grafo

Una spec aislada aporta poco. Cuando declara de qué depende, una herramienta puede contestar preguntas que antes exigían convocar una reunión. Las relaciones se escriben en dependencies (o en activates y equips cuando se trata de trabajo) y tienen un vocabulario cerrado:

RelaciónSignificadoUso típico
implementsRealiza una spec de nivel superiorFEAT → PROD; FLOW → PROC
constrained-byDebe respetar las restricciones de otraDOM → ARCH; FEAT → DOM
extendsAñade detalle en la misma capaDOM-002 → DOM-001
uses-data-fromConsume datos definidos en otraFEAT → DOM
activatesConocimiento inyectado en el trabajoWRK-SPEC → DOM, ARCH
equipsCapacidad agéntica inyectada en el trabajoWRK-SPEC → SKILL, HARN
loadsUn agente carga las skills que puede invocarAGT → SKILL
verifiesUn eval verifica una skill, un agente, un harness o un flujoEVAL → SKILL, AGT, HARN
requiresNecesita una herramienta determinista, con rango semverSKILL requires TOOL >=0.6 <1.0
mechanized-byUna norma la aplica una regla concreta de una herramientaRULE → TOOL, regla broken-ref
distilled-fromDerivada: la spec se reconcilió a partir de un fragmentoDOM → FRAG
derived-fromDerivada: entradas fijadas de una proyecciónPROJ → DOM@1.2.0
runsDerivada de los pasos de un flujoFLOW → SKILL, AGT, TOOL
supersedesReemplaza a otra specVersión nueva → spec deprecada
depends-onDependencia genéricaCualquier capa

Error frecuente. Escribir a mano runs, distilled-from o derived-from. Las tres las calcula el grafo a partir de otros campos. Si las estás tecleando, hay algo mal planteado.

En el día a día del eje de Conocimiento usarás sobre todo las cuatro primeras y supersedes. Elige la más específica que sea cierta y deja depends-on para cuando ninguna otra describa la relación.

Lo que el grafo permite preguntar

PreguntaComandoCuándo la haces
Qué se ve afectado si cambio esta specspec-graph impact <id>Antes de modificar una spec existente
Qué contexto rodea a esta specspec-graph context <id> --depth NAl preparar un trabajo; es la base de la activación (módulo 3, Eje de Trabajo y activación)
Qué specs han quedado desconectadasspec-graph orphansAntes de cada pull request y en revisiones periódicas

Una spec huérfana, que nadie referencia y que no referencia a nadie, no siempre es un error. Sí es una señal: o le faltan dependencias, o recoge algo tan obvio que nadie la necesita.

Ciclo de vida y confianza

Toda spec de conocimiento recorre tres estados: nace en draft, pasa a active cuando el equipo la da por vigente y termina en deprecated cuando otra la sustituye. Nunca se borra ni se renombra, porque el id es la referencia que usan las demás.

La confianza es un campo distinto del estado. Una spec puede estar active y tener confianza low: está en vigor, pero se apoya en poca evidencia. El valor que declaras tiene un tope que depende de lo que haya en Evidence:

Evidencia disponibleConfianza máxima
Ni revisada ni validada (la regla es inferida)low
Revisada o validadamedium
Revisada y validadahigh

Subir la confianza es un acto humano y gobernado. Se ajusta tras el merge, cuando alguien con autoridad sobre esa spec la ha revisado o la ha contrastado con pruebas, y spec-graph validate avisa si declaras más de lo que la evidencia sostiene. El modelo completo, incluido cómo se distingue lo escrito por una máquina de lo revisado por una persona, está en el módulo 7 (Confianza y evidencia).

Tu primera spec en cuatro pasos

El ejemplo es la regla de límites de transferencia de un banco. Lleva unos diez minutos.

1. Crea el directorio y el fichero.

mkdir -p specs/domain

2. Escribe la cabecera. Una spec recién escrita, sin revisar ni validar, entra en draft y con confianza low:

---
id: DOM-PAY-001
type: knowledge
layer: domain
title: "Límites de transferencia por tipo de cliente"
status: draft
confidence: low
version: "0.1.0"
owner: payments-team
domain: payments
tags: [transfers, limits]
dependencies:
  - id: ARCH-002
    type: constrained-by
---

3. Redacta las cuatro secciones del cuerpo. En Intent, por qué existe la regla. En Definition, la regla misma, por ejemplo que toda transferencia superior a 10.000 € necesita doble aprobación. En Acceptance Criteria, comprobaciones que alguien pueda ejecutar. En Evidence, de dónde sale la regla y quién la ha confirmado.

4. Valida.

spec-graph validate
spec-graph orphans

Si los dos comandos pasan, abre el pull request y etiqueta al owner.

Lista de comprobación antes del pull request

Cabecera

  • El id sigue el patrón TIPO-AREA-NNN.
  • La layer corresponde al type.
  • status y confidence tienen valores válidos.
  • owner es un equipo o una persona real.

Dependencias

  • Cada id referenciado existe.
  • No hay dependencias circulares.
  • La relación tiene sentido semántico: una FEAT no restringe a una ARCH.
  • Si la spec es de trabajo, respeta la regla de los ejes.

Cuerpo

  • Intent explica el porqué, no el qué.
  • Los criterios de aceptación se pueden comprobar.
  • Evidence cita fuentes reales.

Validación

  • spec-graph validate pasa.
  • spec-graph orphans no señala la spec nueva.
  • Si modificas una spec existente, subes la versión.
  • Si la sustituyes, marcas la antigua como deprecated.

En resumen

  • Cinco capas cubren el arranque: ARCH condiciona, DOM regula, PROD orienta, FEAT describe lo que ve el usuario y DOC explica cómo se hacen las cosas.
  • Una spec que encaja en dos capas se divide en dos.
  • Las relaciones convierten los ficheros en un grafo, y el grafo responde a impacto, contexto y huérfanas sin reuniones.
  • La confianza está limitada por la evidencia: revisada o validada llega a medium; revisada y validada, a high. Subirla es una decisión humana.
  • Ninguna spec entra sin pasar spec-graph validate y la lista de comprobación.

Para practicar

Elegid un módulo de vuestro sistema y repartid el equipo en parejas. Cada pareja escribe en veinte minutos una spec DOM de diez a quince líneas sobre una regla real de ese módulo, con su cabecera completa y al menos una dependencia. Después intercambiad las specs: la otra pareja aplica la lista de comprobación y responde a dos preguntas, qué capa habría elegido ella y qué evidencia haría falta para subir la confianza a medium. Cerrad la sesión dibujando en una pizarra el grafo que forman las specs escritas y marcando las que quedan huérfanas.
